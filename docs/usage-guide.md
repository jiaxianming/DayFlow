# DayFlow 使用指南

> 面向最终用户的系统使用说明与核心概念解读。
> 研发设计文档请见 `docs/superpowers/specs/` 与 `docs/superpowers/plans/`。

---

## 1. DayFlow 是什么

DayFlow 是一款基于 **Spring AI 多智能体**的个人日报 / 周报生成器。

核心理念:你只需随手记录每天**做了什么、学了什么、要做什么**,系统内的 4 个 AI Agent(策划 / 采集 / 撰写 / 审校)就会像真实编辑部一样分工协作,自动把这些零散记录加工成一份结构清晰、重点突出的日报或周报。整个 AI 协作过程全程记录、可视化呈现,**生成过程透明可追溯**。

## 2. 快速上手

### 2.1 标准使用流程

```
① 登录  →  ② 录入数据  →  ③ 生成报告  →  ④ 查看 / 复用
```

1. **登录**
   - 预置账号:`admin / dayflow123`,也可注册新账号。
   - 登录后系统签发 JWT(有效期 7 天),后续请求自动携带。

2. **录入数据(日常、随时)**
   - 在工作区随手录入「活动 / 笔记 / 待办」三类记录。
   - 不必一次写全、也不必按报告格式组织——**记流水即可**,结构化交给 AI。

3. **生成报告**
   - 进入「报告中心」,选择**日报(DAILY)**或**周报(WEEKLY)**,选定**时间范围**,点击生成。
   - 报告生成是**异步任务**:状态为 `GENERATING`(生成中) → `GENERATED`(已完成) / `FAILED`(失败)。
   - 前端通过**轮询**展示三态,Agent 轨迹渐进式呈现。

4. **查看与复用**
   - 报告以 **Markdown** 渲染,可直接阅读、复制。
   - 可查看「**Agent 时间线**」:每个 Agent 的输入摘要、输出摘要、Token 消耗、耗时、重试次数。

## 3. 三大核心概念:活动、笔记、待办

这是 DayFlow 数据录入的三个模块,也是报告生成的三类**原材料**。

### 3.1 概览对比

| 概念 | 数据表 | 关键字段 | 定位 |
| :--- | :--- | :--- | :--- |
| **活动 (Activity)** | `activity` | `content` 内容、`category` 分类、`occurredAt` 发生时间 | 事实流水:"**我做了某件事**" |
| **笔记 (Note)** | `note` | `title` 标题、`content` 正文、`tags` 标签 | 学习沉淀:"**我学懂了某个知识点**" |
| **待办 (Task)** | `task` | `title` 标题、`status` 状态、`completedAt` 完成时间 | 交付项:"**我要完成的任务**" |

> 三者均带 `user_id`(用户隔离)、`created_at` / `updated_at`(自动维护);主键为雪花 ID(BIGINT)。

### 3.2 活动 (Activity) —— 记「动作」

记录你**实际发生过的动作**,是报告里"今日工作流水"的来源。

| 字段 | 含义 | 取值 |
| :--- | :--- | :--- |
| `content` | 活动内容(自由文本) | 例如"修复登录页跳转 bug" |
| `category` | 活动分类 | `WORK` 工作 / `STUDY` 学习 / `MEETING` 会议 / `OTHER` 其他 |
| `occurredAt` | 发生时间 | 用于按时间范围切分报告区间 |

**录入建议**:做完一件事就记一条,顺手选个分类。开会、写代码、看文档、跨部门沟通都可以记。

### 3.3 笔记 (Note) —— 记「知识」

记录你**学到的、沉淀下来的知识**,是报告里"学习成长 / 技术沉淀"板块的来源。

| 字段 | 含义 | 说明 |
| :--- | :--- | :--- |
| `title` | 标题 | 例如"Spring AI ChatClient 用法小结" |
| `content` | 正文 | 较长的学习笔记原文 |
| `tags` | 标签 | **逗号分隔**,如 `spring-ai,java,llm` |

**检索特性**:报告生成时,Collector Agent 会按 Planner 给出的**关键词**在笔记的 `title` / `content` / `tags` 三个字段上做匹配检索(当前为 LIKE 匹配,M3 暂未接入 RAG 向量检索)。

> **录入建议**:标签要写"将来报告里可能用来检索你的词",便于 AI 命中。

### 3.4 待办 (Task) —— 记「成果」

记录你**计划完成、并已经完成的交付项**。

| 字段 | 含义 | 取值 |
| :--- | :--- | :--- |
| `title` | 任务标题 | 例如"对接报告生成接口" |
| `status` | 任务状态 | `TODO` 待办 / `DOING` 进行中 / `DONE` 已完成 |
| `completedAt` | 完成时间 | 标记为 `DONE` 时记录,用于判定是否落入报告区间 |

> ⚠️ **关键规则**:报告生成时**只采集 `status = DONE` 且完成时间落在报告区间内的任务**。`TODO` / `DOING` 的任务**不会进入报告**——报告强调"交付了什么",而非"计划做什么"。

## 4. 三者的关系

### 4.1 没有强关联,共同构成「原材料库」

活动、笔记、待办**相互之间没有外键、没有父子关系**,可以独立录入、独立管理。它们的关联体现在**报告生成流程**中——三者都是 Collector Agent(采集 Agent)的取数来源,共同喂养出一份报告。

```
你录入的 Activity / Note / Task
        │   (均按 userId 隔离 + 时间范围切片,作为报告原材料)
        ▼
┌──────────────────────────────────────────────────┐
│        报告生成编辑部 (ReportOrchestrationService)        │
│                                                    │
│  ① Planner 策划                                    │
│     规划"报告分几块、每块用哪类数据(ACTIVITY/TASK/NOTE)" │
│         │                                          │
│  ② Collector 采集 —— 调用 @Tool 取数:              │
│         │   • listActivities()        ← 活动       │
│         │   • listCompletedTasks()    ← 待办(仅DONE) │
│         │   • searchNotes(keywords..) ← 笔记       │
│         │                                          │
│  ③ Writer 撰写                                     │
│     综合数据,按大纲写出报告初稿                     │
│         │                                          │
│  ④ Reviewer 审校                                   │
│     不通过则触发反馈循环,Writer 重写(最多重试 2 次) │
└──────────────────────────────────────────────────┘
        ▼
     最终报告 (Markdown,存入 report 表,并记录 agent_trace 轨迹)
```

### 4.2 三类数据在报告中的角色分工

| 数据源 | 在报告里回答的问题 | Collector 取数方式 |
| :--- | :--- | :--- |
| **活动** | "**做了什么**" —— 工作流水、会议、协作 | 按时间范围全量,带分类与发生时间 |
| **待办(已完成)** | "**交付了什么**" —— 闭环的产出成果 | 仅 `DONE`,按完成时间筛选 |
| **笔记** | "**学了 / 沉淀了什么**" —— 知识与思考 | 按 Planner 给出的关键词,匹配标题/内容/标签 |

### 4.3 安全设计(数据隔离)

- **按用户隔离**:三类数据均带 `user_id`,你只能看到自己的记录,接口层与数据层双重校验。
- **LLM 全程不接触 userId**:采集工具的 `userId` 一律由后端从 `AgentContext`(ThreadLocal)读取,AI 无法指定或篡改用户,**杜绝 LLM 幻觉导致越权拉取他人数据**;若 `userId` 缺失则安全降级返回空列表。

## 5. 一个完整示例

假设某天你的记录如下:

| 类型 | 内容 |
| :--- | :--- |
| **活动** | 开了需求评审会(`MEETING`)、修复 3 个 bug(`WORK`)、阅读 Spring AI 文档(`STUDY`) |
| **待办** | "修复登录 bug" → 标记 `DONE`;"对接报告接口" → 仍为 `DOING` |
| **笔记** | 写了《Spring AI ChatClient 用法小结》,标签 `spring-ai,java` |

晚上点击「生成日报」,后台编辑部这样工作:

1. **Planner** 规划板块:今日工作 / 完成事项 / 学习成长 等。
2. **Collector** 按板块取数:
   - 活动全量取来当**工作流水**(会议、修 bug、读文档);
   - 待办只取 `DONE` 的"修复登录 bug"作为**交付**;"对接报告接口"未完成,**不会进报告**;
   - 笔记可能被关键词 `spring-ai` 命中,作为**学习亮点**。
3. **Writer** 综合写出日报初稿。
4. **Reviewer** 审校,通过即定稿;不通过则 Writer 重写(最多 2 次)。

最终你得到一篇结构完整、有事实有成果有学习的日报。

## 附:相关接口速览

| 模块 | 路径 | 说明 |
| :--- | :--- | :--- |
| 活动 | `/api/activities` | CRUD + 分页(GET/POST/PUT/DELETE) |
| 待办 | `/api/tasks` | CRUD + 分页 |
| 待办完成 | `PATCH /api/tasks/{id}/complete` | 标记任务为 `DONE` |
| 笔记 | `/api/notes` | CRUD + 分页 |
| 报告生成 | `POST /api/reports/generate` | 异步触发生成 |
| 报告轨迹 | `GET /api/reports/{id}/traces` | 查询 Agent 协作轨迹 |
| 鉴权 | `/api/auth/login`、`/api/auth/register` | 登录、注册 |

> 所有接口统一返回 `Result<T>` 包装(`code` / `msg` / `data`,成功 `code = 200`),路径前缀 `/api`,JSON 字段 camelCase。
